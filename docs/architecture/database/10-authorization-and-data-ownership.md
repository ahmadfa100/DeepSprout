# 10 — Authorization and data ownership

Authentication establishes `PersonId`; it is never inferred from an email query parameter or browser role flag. Verified `PersonEmail` supports invitation matching. An API policy evaluates **actor Person + selected active grant + exact resource owner/scope + operation + consent/entitlement when applicable** for both reads and writes. The workspace switcher is a view of grants. Global Admin is privately provisioned and audited; routine owner operations remain owner-authorized even for Admin unless a specific governance command exists. A paying subscription cannot create a grant.

| Data | Owner and ordinary readers | Denied by default |
|---|---|---|
| Lab responses/scores, Recovery, Shield telemetry, personal routine | Person; narrow explicit exceptional legal/admin procedure | Coach, Institution, Provider, Supervisor, ordinary Admin browsing |
| Initiative applications/memberships/groups/forms | Institution Representative; active Initiative Supervisor where function allows; assigned Coach sees only assigned group operational subset; own applicant sees own record | Other institutions, unrelated Coach, Provider, public |
| Assignments/submissions/reviews | Student owns own view; current assigned Coach operational view; Initiative Supervisor/Rep permitted reports and restricted drilldown | Other group members, revoked Coach future roster, public |
| Feedback vs internal note | Student-visible `ReviewDecision.Feedback` vs restricted `ReviewPrivateNote` | Student cannot fetch private note by ID |
| Provider booking/safety/attendance | Provider staff and appointed Supervisor in named resource/session/cohort; participant sees own | Linked Institution receives only approved scope/projection |
| Excuse file and sensitive form answer | Subject, active named operator, Representative final decision as policy | General Coach roster, public listings, broad exports |
| Garden/Insights | Person sees own; GroupGarden members/staff see scoped collective aggregate | Group view never exposes private Lab/Shield; limited Student has no Personal Garden |

For an Initiative action, resolve `Initiative.InstitutionId`, then verify an active `RepresentativeMembership` or `InitiativeStaffAppointment` for that `InitiativeId` and permitted role. Supervisor may approve one application and manage groups, but only Representative may reject/remove/suspend/restore/block or revoke staff. Attendance requires a current active duty covering the exact session; a published session may exist without one but records no attendance until staffed. An Institution Session with no Initiative uses its own `StandaloneSessionSupervisorAppointment`, never a borrowed Initiative grant. For Coach action, resolve Group XOR parent: Program owner/authorized Coach or Initiative group allocation plus active Initiative Coach appointment. For Provider action, resolve `Experience.ProviderId` and active Provider membership or appointment/session scope. Revocation must invalidate cached grants and recheck in each command/read; author IDs remain on history. A Program/Experience link exposes only the agreed projection under `ScopeVersion`, never underlying owner tables by default.

Guard before loading sensitive material and again immediately before mutation. APIs return indistinguishable not-found/denied errors where revealing resource existence is unsafe. Apply field-level DTOs for student vs internal note and aggregate vs raw form/browsing data; never serialize EF entities directly. Signed, short-lived booking credentials identify a single registration/session, are validated server-side with nonce/use record and window, and do not themselves grant operator authority. Audit sensitive reads, exports, Admin decisions, grant changes and file access. Data retention/deletion and minor consent are jurisdiction-specific open decisions; schema supports subject ID, versioned consent, file purpose and retention metadata without claiming a legal rule.
