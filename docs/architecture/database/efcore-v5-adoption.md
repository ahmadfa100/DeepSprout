The older `DeepSproutDbContext` (129-table M1) and its 24 migrations stay in `src/DeepSprout.Infrastructure/Migrations` unchanged, because `DeepSprout_Validation` records them. They are history, not the target. See [historical M1 database](historical-m1-validation-database.md).

## Migrations

**`V5Baseline` (v5-lean-1).** Up runs the approved DDL in GO batches, so a new database matches `DeepSprout-v5-FULL-Database.sql` exactly, including the `ds_app` role and insert-only permissions. It refuses an M1 database (error 51100) and any non-empty database (51101). Down refuses (51102): the baseline is never rolled back by a migration; restore a backup instead.

**`V5Lean2Onboarding2AndV41` (v5-lean-2).** Generated by EF from the model change, then extended by hand:

| Change | Rule it implements |
|---|---|
| `IndividualProfile.JourneyLevel int NOT NULL DEFAULT 1`, `CHECK (JourneyLevel >= 1)` | Every journey starts at Level 1 |
| `CK_IndividualProfile_SetupAnswers`: answers and version together; version ≥ 1; JSON object | Versioned six-answer contract |
| `CK_IndividualProfile_Stage` adds `QuickSetup`, `Story`, `Home`; keeps legacy stages | Onboarding 2.0 stages |
| `CK_PlanRevision_Accepted`: Draft has no acceptance time; Accepted/Superseded must have one | Explicit activation is recorded |
| `org.Organization.Kind IN ('Institution')`; Provider rows re-homed, each recorded in `ops.AuditEvent` | v4.1: Institution-only partners |
| `org.VerificationCase.Kind IN ('Institution','Coach')`; Provider cases re-homed and audited; Coach kept as legacy history | v4.1: Institution verification only |
| `org.StaffAppointment`: `RequestedByPersonId` dropped, `Requested` removed, invitation fields required | v4.1: invitation-only, no self-request |
| `provider.Experience.ProviderId` renamed to `OrganizationId` (rename, not drop and add) | v4.1: Institution-owned outdoor activities |
| `DENY INSERT, UPDATE, DELETE` on `coach.CoachProgram` and `partnership.PartnershipLink` for `ds_app` | v4.1 retirements without deleting history |

Up stops before changing anything when existing rows would break a new rule: self-requested or incomplete staff appointments (51110, 51111), setup answers without a valid version (51112), inconsistent plan acceptance (51113). It never guesses a value.

Down is protective. It refuses when any profile has an Onboarding 2.0 stage or a Journey Level above 1 (51120). Otherwise it restores the previous constraints, re-adds the nullable `RequestedByPersonId`, renames the column back, revokes the retired-table denies, and sets exactly the audited rows back to `Provider`, recording the rollback in `ops.AuditEvent`.

## Commands

```sh
# Model only (no database connection needed)
dotnet ef migrations has-pending-model-changes --context DeepSproutV5DbContext --project src/DeepSprout.Infrastructure --startup-project src/DeepSprout.Infrastructure
dotnet ef migrations script --idempotent --context DeepSproutV5DbContext --project src/DeepSprout.Infrastructure --startup-project src/DeepSprout.Infrastructure

# A new, empty database
set DEEPSPROUT_V5_CONNECTION=Server=localhost;Database=<new database>;Integrated Security=True;Encrypt=True;TrustServerCertificate=True
dotnet ef database update --context DeepSproutV5DbContext --project src/DeepSprout.Infrastructure --startup-project src/DeepSprout.Infrastructure
```

## Adopting `DeepSprout_V5_Demo` (prepared, not run)

1. Take a verified copy-only backup (`BACKUP DATABASE … WITH COPY_ONLY, CHECKSUM`, then `RESTORE VERIFYONLY … WITH CHECKSUM`).
2. Run `submission/adopt-v5-baseline.sql` in the database. It checks a SHA-256 fingerprint of every column, CHECK, FK and index against v5-lean-1 (`0x4E7EA1C7…5394DE4`), records `V5Baseline` as applied, and changes no table or row. It is idempotent and refuses any other schema.
3. Review `submission/DeepSprout-v5-UPGRADE-lean1-to-lean2.sql` (the idempotent script of the second migration), then apply it with `dotnet ef database update` or that script.
4. Re-run `submission/DeepSprout-v5-NEGATIVE-TESTS.sql` (40 rolled-back tests) and compare row counts with the pre-upgrade counts.

Rollback: `dotnet ef database update V5Baseline` (protected as above). To undo the adoption itself, delete the single `V5Baseline` history row.

## Verification (8 November 2026, disposable databases on DESKTOP-A4AL2KR)

| Test | Result |
|---|---|
| Live `DeepSprout_V5_Demo` vs a fresh build of the committed v5-lean-1 script: tables, columns, checks, FKs, indexes | Identical (58 / 759 / 143 / 147 / 267) |
| Generator reproduces the committed script | Identical except the 31-line header comment the owner removed in `f3b0617`; the generator now omits it |
| EF model DDL (`dbcontext script`) vs live `DeepSprout_V5_Demo`: types, nullability, defaults, identity, check definitions, FK columns and delete rules, index columns, uniqueness and filters | Identical; only the role permissions differ, and the migrations add them |
| Fresh database via `V5Baseline` + `V5Lean2` vs fresh build of the v5-lean-2 script | Identical, including permissions; fingerprint `0x52B723DF…5F640435` on both |
| Clone of `DeepSprout_V5_Demo`: adopt, then upgrade | Adopted; upgraded; every table's row count unchanged except `ops.AuditEvent` +2 (the two re-homed rows); fingerprint = v5-lean-2 |
| Same clone: roll back to `V5Baseline`, then upgrade again | Fingerprint back to v5-lean-1; Provider kinds restored from the audit trail; re-upgrade succeeds |
| Guards: M1-shaped database; unversioned setup answers; rollback with a `Home` profile | Refused with 51100, 51112 and 51120; transaction rolled back; schema unchanged |
| Adoption script: re-run; wrong schema | "Already adopted"; refused with 51201, nothing recorded |
| v5-lean-2 negative tests (40) on a fresh build | 39 PASS, 0 FAIL, 1 INFO |

UNIQUE constraints in the SQL script are UNIQUE indexes in the EF model. The catalog compare treats both as unique indexes with the same name, columns and filter. A future EF migration that drops one of the original constraints must use `DropUniqueConstraint`, not `DropIndex`.
