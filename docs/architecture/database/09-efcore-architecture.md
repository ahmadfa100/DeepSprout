# 09 — EF Core architecture

## Recommended shape

Start with **one `DeepSproutDbContext`** and module-owned `IEntityTypeConfiguration<T>` classes, each mapped to its SQL schema. This keeps admission/booking/reward/outbox transactions and one migration stream simple while the backend is new. Module services expose commands/read contracts; no controller reaches another module's DbSet directly. Split DbContexts only when measured ownership/deployment needs outweigh cross-context transaction and migration complexity. A shared database with several contexts is possible later, but overlapping EF migrations on the same tables are a significant risk. There is no EF project here today.

Use private setters/factory methods on aggregate roots for legal transitions; repository abstractions only where domain-specific persistence behavior is needed. `DbContext` already supplies change tracking and unit of work, so avoid generic repository/unit-of-work boilerplate. Map `TimeWindow`, `MoneyDisclosure`, consent/version markers and evidence provenance as owned/complex types only when their columns are genuinely local to one owner; use explicit entities for versioned shared values. Store cross-aggregate references as IDs and load purpose-built projections, not huge eager navigation graphs. Avoid lazy loading for security-sensitive data.

Configuration conventions: `HasKey`, explicit `HasAlternateKey` for same-owner composites, `HasIndex(...).IsUnique().HasFilter(...)` for active uniqueness, `HasCheckConstraint` for XOR/range/state, `OnDelete(DeleteBehavior.Restrict/NoAction)` for history, and `IsRowVersion()` for mutable roots. Map status strings with constrained lengths/converters; reject unknown values at API boundary. Global query filters are appropriate for a narrow soft-deleted *draft* subset and perhaps a current publication view; they are **not** a replacement for scoped authorization and can hide historical records from audits. Tenant/owner filters should be explicit in read services and tested with malicious IDs.

`SaveChanges` interceptors can collect domain events and stamp timestamps, but should not send messages or issue rewards outside the DB transaction. Insert `OutboxMessage` and `AuditEvent` with the state change. An idempotent hosted worker dispatches after commit and marks delivery; background jobs expire offers under the same capacity service. Use explicit `BeginTransactionAsync`, narrow SQL lock hints/interceptor or stored allocation command for capacity, and EF execution strategy around the entire transaction where retries are safe. `DbUpdateConcurrencyException` yields a reread/409 or controlled retry. Never assume EF optimistic tokens enforce aggregate counts.

Migrations are ordered by dependency: identity → owners/version tables → memberships/capacity → evidence/operations → projections, with data/backfill and expand-contract phases. Test every migration on a representative SQL Server copy, including filtered indexes, composite FKs, locking and rollback plan. Seed only immutable reference codes, approved baseline catalog versions and safe dev/demo fixtures in separate development setup. Do not seed fake production people, prices or clinical thresholds. For reporting use `AsNoTracking` projections, explicit source/denominator/version, pagination and temporal ranges; materialize `ReportSnapshot` only after measurement shows repeated costly reads. Preserve query filters/privacy in every projection.
