# 08 — SQL Server physical design

## Database, keys, naming

Use one SQL Server database with bounded-context schemas (`iam`, `lab`, `recovery`, etc.) and a modular ASP.NET Core deployment. Cross-schema FKs and local transactions are valuable for the approved cross-workspace workflows. Do not partition databases by workspace or introduce distributed transactions now. Use singular PascalCase tables, `Id` internal PKs, `...Id` FKs, UTC suffixes and explicit `CK/UQ/IX` names. **Clustered `bigint IDENTITY`** keeps inserts/indexes narrow and stable. Exposed aggregates additionally receive random application-generated `uniqueidentifier PublicId`, unique and immutable; avoid exposing enumerable identity values. Sequential GUID or UUIDv7 could improve GUID index locality, but is unnecessary for clustered keys; if selected later, validate provider support and collision/ordering semantics. Imported browser IDs live in a controlled migration alias map during rollout, not as primary keys. Do not recycle identifiers.

`datetime2(3)` UTC is the default instant; retain IANA/Windows mapped time zone ID and `date` local schedule day for windows. `datetimeoffset` is appropriate only for an external timestamp whose original offset is itself evidence; also persist normalized UTC. Use `decimal(19,4)` for monetary disclosures, `char(3)` ISO currency, `nvarchar(n)` bounded labels, `nvarchar(max)` for actual long narratives, `bit` for true booleans, `varbinary` for hashes, and opaque object-store references for media. Status codes are strings with checks or controlled lookup/version rows, never persisted C# enum ordinals. Nullable columns mean genuinely absent/not yet known; an unavailable usage period is not a zero-valued period. Use row/page compression only after measurement.

## Referential integrity and indexing

All mandatory owner/subject references are FK constrained; use `NO ACTION` for published history and explicit archival. Composite alternate keys enforce same-parent relationships (`GroupId+InitiativeId`, `MembershipId+InitiativeId`, `BookingId+ExperienceId`, `OfferId+ExperienceId`) and require a pinned published revision to belong to its Application, Program, Session or Experience owner. XOR checks enforce the two permitted Group and GroupGarden owner kinds. Filtered unique indexes enforce one active appointment/offer/seat holder, one reward grant per source/effect/beneficiary, and one active verified email. They **do not** enforce the 135/3/global capacity sums; those use locked transactions. Unique business keys must be normalized before insert and races handled as conflicts. Indexed access paths follow admission queue, scoped roster, due work, offer expiry, time-window reporting and per-person history in the dictionary. Verify actual plans and avoid indexing every FK blindly if no query uses it.

## Capacity representation and locking

`InitiativeSeat`, `ExperienceSeat`, and `SessionSeat` are numbered capacity slots. For a capacity `N`, exactly `N` slots exist; a free slot has no current holder. A held slot references a live offer; an occupied slot references a membership/booking/registration. Create/remove slots only in a transaction that locks the owning Initiative/Experience/pool and refuses removal of held/occupied slots. Initiative slots have `SlotNo<=135`, so even bad capacity values cannot create a 136th slot. Provider/session capacity is published resource policy, not a new platform-wide numeric limit. The slot model costs rows but makes held+confirmed ≤ capacity a direct relational invariant under a serialized allocator. Time expiry still requires the command/job to clear a held slot; an expired but unprocessed offer temporarily reduces availability, which is safe and should be reconciled promptly.

For allocation: begin transaction; lock owner row and eligible slot range with `UPDLOCK,HOLDLOCK` (or `SERIALIZABLE` on the narrow allocation query), recheck current status/eligibility/expiry, choose a free slot, update holder, update application/booking and offer/membership, append audit/outbox, commit. Lock all operations in a documented order: owner → slot → application/booking → offer/appointment → audit/outbox. RowVersion detects stale edits and gives clear retry/conflict responses, but **RowVersion alone cannot prevent write skew across distinct seat rows**. Unique indexes remain the last line of defense. Deadlock 1205 and transient 2601/2627 are retried only for idempotent commands with bounded jitter and a fresh state read. Do not repeat a non-idempotent external send inside the transaction.

## Security and operations

Application DB principal has least privilege for runtime schemas; migration principal is separate. Parameterize queries, use TLS and encryption at rest, encrypt sensitive object-store files with managed keys, rotate credentials, and prohibit raw assessment answers/browser data in logs. SQL Row-Level Security could add defense in depth for a few simple tenant tables, but it does not replace endpoint resource checks or solve cross-owner links and personal privacy. Encrypt/hash OTP/invite secrets and QR credentials; protect token lookup with rate limits. Separate restricted query paths and access audit. Retention windows, lawful deletion, minor consent and export need approved policy before implementation. Backups require restore drills; outbox and audit need monitoring and retention.
