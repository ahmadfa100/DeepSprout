## Domain model and aggregate boundaries

One `iam.Person` holds verified contacts and separately granted global or resource authority. `Institution`, `Provider` and `CoachProgram` are distinct ownership roots. An Institution owns Initiative admission, staff and groups; a Provider owns experience inventory and safety; an independent Coach owns Program stages, membership and assignments. `coach.OperationalGroup` has exactly one `InitiativeId` or `ProgramId`, with parent-specific participation records. Shared `task.Assignment` stays group-scoped, with immutable revision, recipient, attempts and decisions. Session registration, factual attendance, excuse and completion are separate facts. Provider booking and offer are separate from Institution application. Partnership tables link originals rather than copy them. Evidence originates from authoritative facts, and reward entries reference evidence and published policy. `evidence.GroupGarden` belongs to one Initiative or one independent Coach group; Provider has none. Reports read authorized operational facts. AI receives only allowed, purpose-filtered summaries and cannot mutate recovery, scoring, admission, rewards or grants.

**Membership definition.** `Accepted` and `Suspended` are effective Initiative membership states; suspension retains membership and the capacity claim. `Withdrawn`, `Removed`, `Completed` are historical ended states and require `EndedAtUtc`. A filtered unique index on `PersonId` for `Accepted`/`Suspended` makes concurrent acceptance into two Initiatives fail. The old unique `(InitiativeId,PersonId)` can remain for one membership per Initiative; rejoining after an ended membership is a separate policy decision. Application `Pending` is not membership. Multiple Pending applications are not prohibited by the new decision; define that policy separately if desired. To switch, end the former effective membership under the applicable authority/cutoff, then submit and approve the new application; one transaction cannot create overlap even briefly. The new Initiative must still pass eligibility, authority and capacity checks.

**Five-day rule.** Recommend compare a server UTC instant with `StartsAtUtc - 120 hours`, and allow ordinary voluntary withdrawal only when `SYSUTCDATETIME() < DATEADD(day,-5,StartsAtUtc)`. This is a recommendation, **not an owner-approved interpretation**. If the owner chooses five local calendar dates, calculate against the Initiative's stored time zone with a documented DST rule and persist the resulting cutoff UTC at publication. Pin an accepted member's cutoff/terms revision, and decide whether a later reschedule can reopen or close withdrawal. Never infer an exception from `Removed`/`Completed`; Representative administrative actions remain distinct. Pending application withdrawal is allowed irrespective of this cutoff. Reapplication after rejection or withdrawal, and multiple Pending applications, need narrow policy decisions; retain distinct application attempts/decision history so the schema can implement either choice.

**Capacity strategy.** Remove numbered `InitiativeSeat`, `SessionSeat`, `ExperienceSeat`. Use authoritative membership/registration/booking/offer rows, with *all* allocator commands serialized on the parent row (`UPDLOCK,HOLDLOCK`) before counting and writing. The runtime principal receives EXECUTE on allocator procedures and SELECT on facts, not direct INSERT/UPDATE/DELETE on capacity-bearing tables. This is a database-enforced write boundary, not merely a convention in the UI. `Capacity` has CHECK 1..135 for Initiative; Session pool and Experience have positive capacities. Count active claims, including `Accepted`/`Suspended` and held unexpired offers; if a historical `Completed`/`Removed` membership retains its claim under the interim non-recycling default, carry an explicit `CapacityReleasedAtUtc` (nullable) and count rows where it is null. Voluntary prestart withdrawal releases it. Administrative removal, completion, cancellation and rescheduling release/retain claims only under a published policy/authorized command. Expiry worker changes an `Offered` row to `Expired` under the same parent lock; time passing alone does not free capacity until that transition, which is safe but may temporarily underfill. A confirmed booking and its accepted offer must never be double-counted: count `Confirmed` booking plus only `Offered` offers whose booking is still queued/offered. The same pattern applies to Session pools, except no offer table exists there. A count query under the parent lock is simpler than stored counters at the approved scale and cannot drift from its source rows. A counter plus CHECK can reject over-cap updates, but cannot prove its value equals membership/booking facts without triggers or exclusive stored-procedure writes and reconciliation. If profiling later demands counters, add them as cached allocations with transactional updates and scheduled source reconciliation.

**Lock order:** resource owner → affected grant → application/booking/offer → person/participant → roster/capacity facts → audit/outbox. A revocation command must lock the same owner before the grant, so authorization cannot race a revocation. For two Initiative roots during a switch, lock ascending ID. Use `READ COMMITTED` with parent `UPDLOCK,HOLDLOCK` or `SERIALIZABLE` on the scoped operation; the filtered Person index is the final one-membership arbiter. Locking only a count under ordinary isolation is unsafe. Unique 2601/2627 and deadlock 1205 are retried only after rereading state under a stable command idempotency key. A rowversion detects stale edits to one row but not cross-row write skew. `IdempotencyRecord` becomes needed with public retryable commands and asynchronous delivery; first-slice procedures use natural unique keys and explicit state checks, and the API must add a persisted idempotency key before external retries are enabled.

**Rewards:** write source fact, `EvidenceEvent`, eligible personal/group grant or reversal, audit, and outward notification outbox **in one SQL transaction** for in-database deterministic rules. This prevents an avoidably stale Garden. The owner aggregate or person row is locked for bounded effect caps. Reward uniqueness is `(EvidenceEventId, beneficiary, EffectCode)` for a Grant, independent of policy version; a correction appends an invalidating event and one linked reversal. Expensive re-evaluation may run later only if it has explicit pending state, replay semantics and a documented consistency contract. Outbox is for external email/push or cross-system integration, not required to update the same database's Garden. Garden state can be queried from ledgers initially. Four practice-type trees are a rendering projection over typed entries, not four tables.

## Physical and security rules

Use separate SQL schemas per owner module, one migration stream and one EF Core DbContext at first. Internal clustered `bigint IDENTITY`; immutable `uniqueidentifier PublicId` on externally addressed roots. `datetime2(3)` UTC for instants; store IANA zone plus local date where wall-clock behavior matters. Names/notes bounded `nvarchar`; `decimal(19,4)` monetary disclosure; `varbinary` hashes only; no raw credentials or file bodies. Rowversion on mutable roots. Published versions and business-history rows are append-only via runtime permissions and guarded update/delete policy. All foreign keys `NO ACTION` unless a prepublication draft cleanup has a specific approved path. Separate migration and runtime principals; runtime gets least privilege and procedures for capacity/authority transitions. Sensitive Lab, Shield, Recovery, excuse and file reads require purpose-specific queries, resource authorization and access audit; partner links do not grant entire participant records. Encryption in transit/at rest and object-store keys are required, but the SQL metadata alone does not prove privacy. Never use subscription entitlement as a resource grant. AI receives allowlisted, minimized projections with purpose, retention and provider contract; no database credentials and no private Lab/Recovery/Shield fields in Supervisor summaries.

**AI Insights contract:** an application service receives authenticated actor, exact resource scope, approved purpose, time window, source definition versions and an allowlisted projection of already-authorized facts. It records the source IDs/coverage used for an explanation and labels generated wording as advisory. The response cannot carry a command token or write through the domain services. Person-facing explanations may use their own private data only under their consent/purpose; Supervisor summaries use aggregate Initiative/Group operational data with small-cell/privacy suppression and no private Lab/Recovery/Shield payload. A third-party provider requires an explicit field-transfer, deletion, retention, security and consent agreement before enabling that route. No chatbot history or broad AI database table is justified now.

**SQL-enforced:** PK/FK/composite FK, XOR checks, positive capacities, Initiative cap 135, filtered one-effective-membership index, unique source reward grant/reversal, one active appointment per Person/Initiative/Role, and grants/permissions on capacity procedures. **Transactional domain logic:** eligibility, actor grant freshness, five-day interpretation, count under parent lock, max three active Supervisors, time-based offer expiry, version publication, reward policy, cross-source completion and file authorization. A CHECK cannot compare counts across tables; filtered uniqueness cannot enforce `COUNT<=3` without serialized command/procedure or an approved alternative slot model.

SQL Server's [filtered index syntax](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17) supports `WHERE ... IN (...)` and uniqueness within the filtered rows. Microsoft also documents [stored-procedure ownership chaining](https://learn.microsoft.com/en-us/sql/relational-databases/tutorial-ownership-chains-and-context-switching?view=sql-server-ver17); the migration must verify that the runtime principal cannot write protected tables directly while it can execute the intended procedures. Required filtered-index `SET` options are explicit in the DDL script.
