# تقرير بوابة الهندسة النهائية — DeepSprout Database Architecture v2

**التاريخ:** 30 أكتوبر 2026. **القرار:** **NO-GO للشريحة الأصلية ذات 18 جدولًا**. هذا تقرير مراجعة قبل التنفيذ، وليس شهادة جاهزية إنتاجية. بقيت حزم v1 وv2 الأصلية دون تعديل. التصحيح المقترح في هذه الحزمة يضيف سجل مسودة واحدًا، فيصبح جرد الهدف 129 جدولًا والشريحة المصححة 19 جدولًا بسبب حاجة وظيفية محددة، لا بسبب هدف عددي. لم يُنشأ Backend API ولم تُنفّذ الجداول المؤجلة.

## 1. عيوب المخطط المؤكدة

| الرمز | الخلل في v2 | الأثر والتصحيح المحدد |
|---|---|---|
| S1 | `Initiative` تشترط `Title/Mode/Capacity/TimeZoneId` من أول إدراج، و`InitiativeRevision` تشترط شروط النشر كلها؛ لا يوجد سجل مراحل الـBuilder غير المكتملة. | مرحلة حفظ مبكرة، بما فيها المرحلة الأولى قبل العنوان، لا يمكن تمثيلها. أضفت `InitiativeDraft` بمحتوى JSON مستقل لكل مرحلة و`rowversion`، وجعلت حقول العرض في جذر المبادرة قابلة للقيمة الفارغة أثناء المسودة فقط. النسخة المنشورة تحفظ القيم الأساسية ولقطة المراحل كاملة، وتبقى غير قابلة للتعديل. |
| S2 | `UQ(InitiativeId,PersonId)` في `InitiativeMembership` يفرض مشاركة واحدة طوال العمر، بينما `InitiativeApplication.AttemptNo` وقراراتها تحفظ محاولات متعددة. | القيد يحسم إعادة الانضمام ضمنيًا رغم أن السياسة مفتوحة، ويجعل قبول محاولة لاحقة يفشل بمفتاح فريد. التصحيح يحفظ `UQ(ApplicationId)` و`UXF(PersonId)` للحالتين الفعالتين، ويزيل التفرد التاريخي الشامل. **لا يُتاح أمر إعادة تقديم أو إعادة انضمام** حتى يعتمد المالك سياسته؛ إجراء الموافقة يرفض وجود عضوية سابقة للمبادرة صراحة. |
| S3 | قرار الطلب يملك FK مستقلًا للطلب وFK مستقلًا للمراجعة، فيمكنه تسجيل `TermsRevisionId` آخر للمبادرة نفسها. | إضافة مفتاح بديل `Application(Id,InitiativeId,TermsRevisionId)` وربط القرار به بمفتاح مركب واحد. تبقى القرارات صفوفًا غير قابلة للتعديل لكل محاولة، و`Application.Status` ملخصًا يُحدّث في المعاملة نفسها. |
| S4 | `AssessmentAttempt.WindowId` و`PersonId` مرجعان مستقلان. | يمكن تسجيل محاولة شخص ضمن نافذة شخص آخر. المفتاح `AssessmentWindow(Id,PersonId)` وFK `(WindowId,PersonId)` يغلقان ذلك؛ النافذة الفارغة تبقى مسموحة للمحاولة الأساسية. ربط `IndividualProfile.LastAssessmentAttemptId` بالشخص نفسه أيضًا. |
| S5 | `ProtectionSession` و`BrowserUsagePeriod` يسمحان بتركيب `InstallationId` و`ConfigurationId` لشخصين مختلفين؛ `BrowserUsageDomain` لا يثبت أن النطاق مختار في التكوين المربوط بالفترة. | إضافة `PersonId` للفترة، والمفاتيح `(Id,PersonId)` للتثبيت والتكوين، وFKين مركبين في الجلسة والفترة. إضافة `ConfigurationId` لسجل النطاق وربطه بالفترة وبـ`ShieldSelectedDomain(ConfigurationId,DomainCode)`. |
| S6 | توجد أزواج موارد أخرى غير مربوطة بالمالك نفسه: دور دعوة Initiative، دعوة وتعيين Provider، مشرف cohort، نسخة السؤال والإجابة، rubric حكم المسابقة، وموضوع حدث المكافأة الشخصية. | عُرّفت المفاتيح البديلة وFKs المركبة في القاموس والتدقيق المرفق. فحص سلطة الممثل/المشرف، أهلية الحجز، وجاهزية المكوّن عند النشر يظل أمرًا ذريًا لأنه لا يُعبَّر عنه بـFK. |
| S7 | v2 تتيح `Status='Published'` في الجذر قبل وجود أي Revision، وهذا ما تفعله تجهيزات `002` نفسها. لا يوجد إجراء نشر مسودة ذري أو حارس قاعدة يربط النشر بنسخته. | يجب إدراج النسخة ثم قلب حالة الجذر ضمن معاملة واحدة مع قفل الجذر وإعادة فحص المؤسسة/الممثل والمراحل والمكونات. صلاحية التشغيل لا تكتب الجذر أو المسودة أو النسخة مباشرة؛ يلزم اختبار رفض تعديل/حذف النسخة المنشورة. |
| S8 | قيد `InitiativeMembership` الحالي يسمح بـ`Withdrawn` دون تحرير سعة، ويسمح بتحرير سعة `Removed/Completed` رغم أن السياسة المحافظة في v2 تقول احتفاظهما بها إلى حين القرار. | القيد المصحح يربط كل حالة بـ`EndedAtUtc` و`CapacityReleasedAtUtc` كما في المصفوفة أدناه. تحديثه لاحقًا يتطلب سياسة معتمدة وترحيلًا صريحًا. |
| S9 | قاموس v2 يطلب دمج أعمدة الأصل مع عمود override يدويًا، ويحمل وصف FK دائري قديم لـ`Session.CurrentRevisionId` رغم إعلان حذفه. | [القاموس المستقل](02-canonical-dictionary.md) يسرد الأعمدة النهائية والقيود في كل صف مباشرة، دون عمود override أو أسماء أعمدة مستبعدة. |
| S10 | اختبار البريد الخاطئ في `002` يقبل الخطأ `51034` (اكتمال ثلاثة مشرفين)، وهو لا يثبت رفض البريد الخاطئ `51033`. | يجب تشغيل حالة البريد الخاطئ قبل ملء المقاعد الثلاثة، وأن تتوقع `51033` وحده. هذا خلل في قدرة الاختبار على الإثبات، وليس فشلًا مرصودًا من SQL Server. |

## 2. عقد الـBuilder ذي المراحل الست

1. ينشئ الممثل المخوّل `Initiative(Status='Draft')` مع `InstitutionId` وهوية عامة، ولو لم يكتب عنوانًا بعد، وسجل `InitiativeDraft(Status='Draft')` واحدًا فعّالًا. `LastSavedStage` يعني آخر شاشة محفوظة، ولا يدّعي اكتمال كل ما قبلها.
2. يحفظ كل انتقال محتوى مرحلته في `Stage1Json` إلى `Stage6Json`؛ القيم قابلة للغياب وقابلة للتعديل في المسودة فقط. `ISJSON` يمنع JSON مكسورًا، و`RowVersion` يمنع الكتابة الصامتة فوق حفظ آخر. مرحلة المراجعة تقرأ هذه اللقطة نفسها وتعيد أخطاء الحقول والمكونات.
3. النشر إجراء واحد يمسك صف المبادرة `UPDLOCK,HOLDLOCK` ويعيد التحقق من مؤسسة موثقة، وممثل فعّال، وحقول المراحل الست، والتواريخ/الموافقة/الأهلية والسعة، ومكوّن عام جاهز حيث يلزم. غياب مشرف فعّال تحذير وتعطيل لتأكيد الحضور، وليس مانع نشر عام.
4. تُدرج `InitiativeRevision` جديدة بقيم العنوان والنمط والسعة والوقت وشروط الجمهور/الكلفة/الإكمال و`PublishedSnapshotJson` كامل، ثم تُحدث قراءة الجذر إلى `Published` وتُربط المسودة بالنسخة، مع Audit/Outbox، قبل `COMMIT`. النسخة المنشورة تُقرأ بحسب أعلى `RevisionNo` منشور، ولا تُحدَّث أو تُحذف من صلاحية التطبيق.
5. تحديث مبادرة منشورة يبدأ مسودة جديدة مع `BaseRevisionId`، ولا يغيّر النسخة القديمة أو شروط طلب/عضوية مثبتة عليها. بيانات Session/Form/Competition/Partner التي تحتاج FK فعليًا لا تُعلن جاهزة بمجرد وجودها في JSON؛ نشر هذه المكونات ينتظر جداولها وإجراءاتها في الشرائح اللاحقة. لذلك الشريحة الأولى تثبت دورة المسودة والنسخة لشروط المبادرة فقط، ولا تدّعي اكتمال الـBuilder التشغيلي كله.

لم تُنفّذ إجراءات `SaveDraft/PublishDraft` أو اختبارات منع تعديل النسخة في SQL الأصلي؛ هذه **تصحيحات مطلوبة قبل GO** وليست وظائف مثبتة في هذه الحزمة.

## 3. المحاولات والقرارات والعضوية

`InitiativeApplication` سجل لكل محاولة برقم `AttemptNo` وبمراجعة شروط مثبتة. `InitiativeApplicationDecision` يحتفظ بتسلسل قرارات غير قابل للاستبدال داخل تلك المحاولة. `InitiativeMembership.ApplicationId` فريد، وFK ثلاثي يثبت أن العضو هو صاحب الطلب والمبادرة نفسها. لا يساوي وجود أعمدة لمحاولات متعددة موافقةً على إعادة التقديم: إلى حين القرار، لا يُتاح أمر المحاولة الثانية بعد `Rejected/Withdrawn/Blocked`، ولا إعادة القبول بعد مشاركة تاريخية في المبادرة نفسها. تستمر القراءة التاريخية كما هي، ويستطيع قيد الشخص الفعّال منع عضويتين فعالتين في مبادرتين مختلفتين حتى تحت التزامن.

### مصفوفة حالة العضوية والسعة

| الحالة الحالية | فعّالة في قاعدة «مبادرة واحدة»؟ | تستهلك سعة المبادرة؟ | الانتقال المسموح والفاعل | تحرير السعة / النهاية |
|---|---:|---:|---|---|
| `Accepted` | نعم | نعم | `Suspended` أو `Removed` بقرار الممثل مع سبب وإشعار؛ `Completed` بمعيار النسخة المنشورة؛ `Withdrawn` بواسطة العضو فقط قبل القطع المثبت | عند `Withdrawn`: `EndedAtUtc` و`CapacityReleasedAtUtc` معًا؛ في غيره حسب الصف التالي. |
| `Suspended` | نعم | نعم | `Accepted` استعادة بواسطة الممثل، أو `Removed` بواسطة الممثل؛ لا انسحاب طوعي ضمن العقد الحالي | الاستعادة لا تغيّر المطالبة؛ الإزالة تنهي الفاعلية وتحتفظ بالمطالبة مؤقتًا. |
| `Withdrawn` | لا | لا | نهائية في هذا السجل؛ محاولة جديدة سياسة مفتوحة | النهاية والتحرير إلزاميان؛ القطع يتحقق من `now < WithdrawalCutoffAtUtc` المثبت وقت القبول. |
| `Removed` | لا | نعم، احتفاظ محافظ مؤقت | نهائية في هذا السجل؛ أثر العودة/تحرير المقعد سياسة مفتوحة | النهاية إلزامية، `CapacityReleasedAtUtc=NULL` حتى اعتماد السياسة. |
| `Completed` | لا | نعم، احتفاظ محافظ مؤقت | نهائية في هذا السجل؛ أثر العودة/تحرير المقعد سياسة مفتوحة | النهاية إلزامية، `CapacityReleasedAtUtc=NULL` حتى اعتماد السياسة. |

السعة المطلوبة لعملية قبول جديدة = عدد عضويات المبادرة ذات `CapacityReleasedAtUtc IS NULL`، ومع طرح عروض الانتظار الحية عند تنفيذها لاحقًا. تحتفظ `Suspended` بمطالبتها. الفهرس الفريد المفلتر على `PersonId` لحالتي `Accepted/Suspended` هو حارس «واحدة فعالة» على مستوى قاعدة البيانات. لا يُستنتج تحرير السعة من كون الحالة نهائية، ولا تحوّل هذه المصفوفة سياسة `Removed/Completed` المؤقتة إلى قرار منتج دائم.

## 4. قرارات المنتج المفتوحة

| الرمز | القرار المطلوب | السلوك الآمن حتى الحسم |
|---|---|---|
| P1 | هل «أكثر من خمسة أيام» تعني 120 ساعة أم خمسة تواريخ محلية؟ وما أثر إعادة الجدولة على العضويات القائمة؟ | يُحفظ موعد قطع UTC في النسخة والعضوية، لكن لا يُفعّل الانسحاب الطوعي الحقيقي حتى يعتمد الاشتقاق وأثر التعديل. |
| P2 | متى يُسمح بمحاولة جديدة بعد رفض/سحب الطلب؟ وهل يُسمح بإعادة الانضمام إلى المبادرة نفسها بعد عضوية تاريخية؟ | منع أمر الإعادة؛ لا يُعاد استخدام Application أو Membership قديمين؛ لا نفترض سياسة إعادة تسجيل. |
| P3 | متى تتحرر مطالبة السعة بعد `Removed/Completed/Cancelled`؟ وهل يختلف الحكم قبل/بعد البداية؟ | الاحتفاظ المحافظ بالمطالبة، مع تجنب قبول زائد؛ لا تحرير صامت. |
| P4 | ترتيب قائمة الانتظار وصلاحية العرض وسباق القبول/الانتهاء | لا تشغيل تلقائي حتى سياسة العرض وإجراء القفل والاختبارات. |
| P5 | موافقات السنّ/الولي، أهلية المشاركة، الاحتفاظ بالبيانات المقيدة، وأثر تغيير شروط النشر | لا جمع حقيقي لبيانات قاصرين أو Lab/Shield الحساسة قبل اعتمادها. |

## 5. التحقق من المفاتيح والملكية

في `001` الأصلي، توجد خمسة FK مركبة (طلب→مراجعة، قرار→طلب، قرار→مراجعة، عضوية→طلب، تعيين→دعوة). أهدافها تملك مفاتيح `UQ` المطلوبة نصيًا، لذا لم أصفها بفشل إنشاء FK. الخلل في **مساواة الحقائق**: FKا القرار المنفصلان لا يثبتان مراجعة الطلب نفسها، وFK التعيين لا يثبت دور الدعوة، بينما FK العضوية الثلاثي يثبت الشخص والمبادرة على نحو صحيح. تحقق الهدف ساكن ولا يثبت قبول SQL Server للسكربت كله.

نفذ مولّد القاموس فحصًا ساكنًا لجميع العلاقات المركبة **المصرّح بها في القاموس المصحح**: 59 FK، وكل عمود محلي/هدف موجود، وترتيب أعمدة الهدف يطابق `PK` أو `UQ` غير مفلتر. [سجل المفاتيح](03-composite-key-audit.md) يذكر كل زوج. من حالات الفشل في v2 التي يغطيها التصحيح: نافذة Lab لشخص آخر؛ تثبيت/تكوين Shield لشخص آخر؛ نطاق خارج تكوين الفترة؛ قرار Application بشروط مراجعة أخرى؛ تعيين بدور يختلف عن الدعوة؛ Cohort/Booking/Appointment بمالك Experience مختلف؛ FormAnswer لسؤال من نسخة أخرى؛ rubric حكم من مسابقة/نسخة أخرى؛ و`PersonalRewardEntry` لحدث شخص آخر. سلطة الفاعل الحالية وجاهزية المحتوى وحالة الحجز والحصيلة المجمعة لا يثبتها FK، وتحتاج أوامر ذرية واختبارات وصول.

استخدمت `UQ` غير مفلتر لأهداف FK لأن [SQL Server يسمح بمرجع FK إلى قيد UNIQUE](https://learn.microsoft.com/en-us/sql/relational-databases/tables/unique-constraints-and-check-constraints?view=sql-server-ver17)، بينما فهرس «عضوية واحدة فعالة» مفلتر، وهو [فهرس UNIQUE على صفوف مختارة](https://learn.microsoft.com/en-us/sql/t-sql/statements/create-index-transact-sql?view=sql-server-ver17)، لا مفتاح هدف للعلاقات المركبة. يدعم SQL Server شرط `IN` في مرشح الفهرس بحسب أمثلة مرجع `CREATE INDEX`، لكن صحة السكربت بعينه لم تُثبت دون محرك.

## 6. اختبارات SQL Server الناجحة

**لا يوجد اختبار SQL Server ناجح في هذه المراجعة.** النجاح الوحيد هو فحص القاموس الساكن (129 جدولًا، 59 هدف FK مركب صالح بنيويًا)، وهو ليس نتيجة تنفيذ DDL أو معاملات أو تزامن.

## 8. التصحيحات المطلوبة قبل إعادة البوابة

1. اشتقاق ترحيل الشريحة الأولى من [القاموس النهائي](02-canonical-dictionary.md) مع `InitiativeDraft`، وتعديل الجذر/النسخة/المفاتيح والقيود المذكورة؛ الإبقاء على v1 وv2 كمرجع تاريخي.
2. بناء أوامر ذات صلاحية تشغيل محدودة لـ`SaveDraft/PublishDraft/SubmitApplication/ApproveApplication` وانتقالات العضوية الإدارية، مع قفل صف Initiative وAudit، ومنع DML المباشر وتعديل/حذف النسخ والقرارات المنشورة. يمكن تأجيل الأمر الإداري إلى سياسة P3، لكن لا يمكن الادعاء باكتمال الحالات قبلها.
3. تصحيح `002`: حالـة بريد خاطئ مستقلة قبل حد المشرفين، واختبارات مسودة كل مرحلة، نشر ذري، نسخة غير قابلة للتعديل، قرار TermsRevision خاطئ، إعادة تقديم مرفوضة، وتحرير السعة بحسب كل صف في المصفوفة.
4. تنفيذ `001/002` الأصليين أولًا على قاعدة تخلصية لتحديد أخطاء SQL الفعلية، ثم سكربتات التصحيح على قاعدة جديدة، مع `sqlcmd -b` وتسجيل إصدار المحرك وخيارات العزل والبصمات والمخرجات وعدد الصفوف. لا تُعالَج أخطاء تنفيذ افتراضية على أنها شوهدت.
5. تشغيل سباقات اتصالين والاختبارات السلبية لكل FK مركب عند ترحيل مجاله. لا توقيع إنتاجي من اختبارات أحادية الاتصال أو فحص وثائق فقط.

## 9. توصية GO / NO-GO

**NO-GO لتنفيذ الشريحة الأصلية ذات 18 جدولًا بوصفها قاعدة الـBuilder والقبول المعتمدة.** يوجد نقص قابل للإثبات في حفظ المسودات، واتساق المحاولات/القرارات والملكية، ومصفوفة السعة؛ و`001/002` لم يُنفّذا على SQL Server. يمكن استخدام القاموس المصحح نقطةَ انطلاق لشريحة 19 جدولًا بعد اعتماد P1–P3 وتشغيل الترحيل والتحقق والسباقات على قاعدة تخلصية. حتى ذلك الحين لا يوجد ادعاء جاهزية إنتاجية أو نجاح SQL Server.
